01 / Requirements & decisions

把本机可用，转化为云端可构建

落地过程中，围绕原生依赖、版本追踪和环境管理完成了四项决策。

  1. 配置 GitHub 流水线

    确认 Gradle、Java、SDK 与 JNI 构建方式，发现 vSomeIP 依赖硬编码在本机 E 盘。

  2. 选择 GitHub 云端 runner

    先消除对本机目录的依赖，再升级为 CI 从源码生成原生库，移除主仓库二进制输入。

  3. vSomeIP 改为子模块

    引用用户已有的定制源码仓库，固定提交；移除源码压缩包与重复头文件。

  4. 使用 Android CLI 管理环境

    替换 setup-android / sdkmanager，提交推送后在 Ubuntu runner 上完成真实验证。

初始约束

  • vSomeIP 含 Android 网络适配及 monolithic 修改。
  • JNI 需要 vsomeip_android_set_network_state 导出符号。
  • Android Automotive 编译需要 android.car.jar。
  • 当前只支持 x86_64 ABI。

最终方案

  • 使用已有定制源码仓库，按 gitlink 固定提交。
  • CI 编译 Boost 与 vSomeIP；主仓库不再保存 .so。
  • Android CLI 安装组件，Gradle 负责构建与测试。
  • 推送、PR 和手动触发共用一条流水线。
工程收益：构建输入、依赖版本和执行结果均有明确记录；新的构建环境无需访问开发机的 E 盘，也无需手工配置仓库 Secrets。
口头汇报要点

此次工作不仅是新增 YAML，还解决了云端无法获取本机定制依赖的问题。源码以子模块固定，原生库由 runner 编译；APK 内库的哈希必须与当次生成库一致。

05 / Troubleshooting & lessons

区分安装状态、命令语法与进程异常

本机 SDK 组件齐全，不代表每一次 CLI 调用都正常；不同终端的路径写法需要分别处理。

问题定位与处理状态
CMD 单引号导致路径异常CMD 保留单引号字面值，CLI 得到 'D:\Android\SDK'，抛出 InvalidPathException；CMD 改用双引号。原因明确
本机 CLI 安装子命令崩溃已有 android-cli.exe 能输出版本和帮助；安装子命令返回 0xC0000409，WER 指向 ucrtbase.dll，真实终端中也复现。具体根因未定位。本机问题待定位
“命令异常”与“组件未装好”混淆核对 SDK 36.1、Build Tools、NDK 和 CMake 版本及关键文件，确认已存在；CMake 与 AAPT2 可运行。组件可用
既有单元测试发现空指针MockVehicleDataSource 停止后，排队回调访问已清空监听器；增加空值检查，状态回调使用读取到的监听器。测试通过
覆盖率与构建输出依赖冲突现有报告任务扫描 app/build；与 assemble 放在同一次调用中触发 Gradle 校验。将报告生成拆为独立步骤。云端验证通过
子模块文档大小写冲突上游同时存在 README.md 与 readme.md；Windows 本地稀疏检出排除重复小写路径，Linux 使用完整检出。本地处理完成

08 / CarLauncher migration scope

迁到 GitLab，主要改编排和环境接入

本项目的构建逻辑已经放在仓库脚本中。建议先复现一个完整 job，再按实际耗时决定是否拆分。

可以沿用的工程内容

  • vSomeIP 子模块与 gitlink 固定提交。
  • Boost 固定版本、源码下载地址及 SHA-256。
  • build-source.sh 中的原生编译命令。
  • verify-artifact.py 的 ELF 与 APK 校验。
  • Gradle Wrapper、JUnit 测试及独立 JaCoCo 报告任务。

必须替换的平台配置

  • 选择 Linux runner，准备 JDK 21、主机编译器、Python 3 与基础下载 / 解压工具。
  • 仍由 Android CLI 安装 SDK / NDK / CMake；显式设置 SDK 目录与 PATH。
  • 将 checkout / setup / upload Actions 改为 GitLab 对应配置和 shell 命令。
  • 配置 push / MR / 手动运行规则，并避免重复创建流水线。
  • 原生产物和报告改用 artifacts；失败日志按需 when: always 保存。
当前接入点GitLab 对应改造
checkout 的 submodules: recursiveGIT_SUBMODULE_STRATEGY: recursive；当前公共 HTTPS 子模块可保留，私有依赖另配访问权限。
$GITHUB_ENV / $GITHUB_PATH改用 CI/CD variables 或同一 job 中的 export；不同 job 重新配置环境。
GITHUB_REPOSITORY + GITHUB_RUN_ID来源记录中的运行链接改用 CI_PIPELINE_URL；提交号仍可由 git rev-parse HEAD 获取。
同一 job 中直接读取生成库拆 job 后通过 artifacts 与 needs:artifacts 传递库；避免依赖共享磁盘残留。
迁移验收仍使用同一组证据：从源码构建、ELF 检查、APK 库哈希一致、220 个 JVM 测试与产物归档。本次只说明迁移方案，未创建或运行 GitLab 流水线。
