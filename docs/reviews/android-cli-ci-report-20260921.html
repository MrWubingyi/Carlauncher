CarLauncher / Android CLI in CI / 02

解决的问题：让云端知道需要什么工具、从哪里使用

项目从开发机迁到 runner，首先需要把 Android 工具链需求从本机配置变为可检查的构建步骤。

原有问题本流程的处理Android CLI 的具体贡献
SDK 目录因机器不同而变化脚本确定 SDK 根目录，并通过环境变量传给后续步骤。接收 --sdk 参数，将组件安装到指定 SDK。
NDK / CMake 等版本依赖隐含在本机YAML 明确列出项目所需的组件名称和版本。通过 sdk install 请求安装所需组件；已有组件可复用。
Automotive 编译需要 android.car.jar安装 Platform 36.1 后，由 shell 检查关键 JAR。提供包含该编译依赖的 SDK Platform；可用性检查由脚本完成。
人工环境准备难以追溯安装命令、CLI 版本和执行结果进入 CI 日志。提供脚本可调用的工具入口；日志保存由 CI 平台承担。

可直接说明的收益

  • 环境要求写入仓库，随变更审查。
  • runner 可按同一组包参数准备环境。
  • 组件缺失在正式构建前暴露。
  • 开发机与 CI 可使用相同命令入口。

证据支持到什么程度

本次成功运行证明：指定 Linux runner 的环境安装与后续构建能够衔接。没有对照实验测量“采用 CLI 后节省多少时间”，也没有证明不同机器产物逐字节可复现。

CLI 安装组件之后，仍须通过文件检查、构建结果和测试结果确认环境有效。工具链版本声明与运行证据共同构成验收依据。

CarLauncher / Android CLI in CI / 04

接入方式：安装入口、传递路径、安装组件、检查可用性

以下命令摘自已验证的工作流。路径传递与文件检查由 Bash 和 GitHub Actions 环境文件完成。

第一步 · Bash 安装 CLI，并加入后续步骤 PATH
curl --fail --silent --show-error --location --retry 3 \
  https://dl.google.com/android/cli/latest/linux_x86_64/install.sh \
  --output "$RUNNER_TEMP/install-android-cli.sh"
bash "$RUNNER_TEMP/install-android-cli.sh"
echo "$HOME/.local/bin" >> "$GITHUB_PATH"
"$HOME/.local/bin/android" --version
第二步 · Bash 确定 SDK，交给后续任务共享
sdk_root="${ANDROID_HOME:-$RUNNER_TEMP/android-sdk}"
mkdir -p "$sdk_root"
echo "ANDROID_HOME=$sdk_root" >> "$GITHUB_ENV"
echo "ANDROID_SDK_ROOT=$sdk_root" >> "$GITHUB_ENV"
第三步 · Android CLI 安装所需组件
android --sdk="$ANDROID_HOME" sdk install \
  platforms/android-36.1 build-tools/36.0.0 \
  ndk/28.2.13676358 cmake/3.22.1 platform-tools
第四步 · Bash 验证关键文件
test -f "$ANDROID_HOME/platforms/android-36.1/optional/android.car.jar"
test -x "$ANDROID_HOME/cmake/3.22.1/bin/cmake"
test -f "$ANDROID_HOME/ndk/28.2.13676358/source.properties"

检查失败会结束对应步骤，避免在缺失工具链的情况下继续构建。

本项目按上面四步集成；无需把 Android Studio 的交互式操作搬进 runner。安装器使用 latest，因此实际 CLI 版本必须以运行日志为准。

安装的每一类组件，都服务于后续明确的构建任务

本流程请求安装 5 类 Android SDK 组件，已有组件可由 CLI 检查并复用，不能从成功结果推断每个包都重新下载。

组件本项目配置谁使用 / 为什么需要
Android Platformplatforms/android-36.1Gradle / AGP 编译 Android API；从 optional 目录读取 Automotive 的 android.car.jar。
Build Toolsbuild-tools/36.0.0提供 APK 构建和打包所需的 Android 工具，由 Android 构建任务使用。
NDKndk/28.2.13676358为 Boost、vSomeIP 和 JNI 提供 Android 交叉编译工具链与运行库。
CMakecmake/3.22.1原生脚本配置 vSomeIP；Gradle externalNativeBuild 配置 JNI 构建。

应用构建基线

compileSdk 36.1 / targetSdk 36 / minSdk 24；当前 ABI 为 x86_64；Gradle 9.5.0、AGP 9.3.1、JDK 21。

版本固定的实际范围

NDK / CMake / Build Tools 版本已写明，Platform 选择 36.1。CLI 安装入口是 latest，Platform Tools 没有固定版本，部分 SDK 包修订也未显式锁定。

因此应称为“版本明确、可追溯的构建”，不能宣称整个环境已完全冻结。

工具：Android CLI 准备

输出：本次构建生成

build/native/artifact/lib/x86_64/libvsomeip3.so

来源记录、ELF 信息、符号、许可证与哈希

原生脚本负责的检查

  • 子模块 HEAD 与主仓库 gitlink 一致，源码状态干净。
  • 校验 Boost 源码包，拒绝复用旧输出目录。
  • 编译静态 Boost 与 monolithic vSomeIP。
  • 验证 ELF 架构、SONAME、动态依赖和网络适配符号。
  • APK 生成后再比较包内 .so 与本次生成库的哈希。
bash tools/vsomeip-android/build-source.sh
bash gradlew :app:assembleDebug :app:testDebugUnitTest
python3 tools/vsomeip-android/verify-artifact.py \
  --apk app/build/outputs/apk/debug/app-debug.apk

没有原生二进制缓存，也没有退回主仓库旧 .so 的路径。

可汇报结论：Android CLI 为源码构建提供所需工具链；“APK 使用了本次源码编译的库”则由构建脚本与哈希检查证明。

Appendix B / GitLab 迁移

迁到 GitLab，主要改编排和环境接入

本项目的构建逻辑已经放在仓库脚本中。建议先复现一个完整 job，再按实际耗时决定是否拆分。

可以沿用的工程内容

  • vSomeIP 子模块与 gitlink 固定提交。
  • Boost 固定版本、源码下载地址及 SHA-256。
  • build-source.sh 中的原生编译命令。
  • verify-artifact.py 的 ELF 与 APK 校验。
  • Gradle Wrapper、JUnit 测试及独立 JaCoCo 报告任务。

必须替换的平台配置

  • 选择 Linux runner，准备 JDK 21、主机编译器、Python 3 与基础下载 / 解压工具。
  • 仍由 Android CLI 安装 SDK / NDK / CMake；显式设置 SDK 目录与 PATH。
  • 将 checkout / setup / upload Actions 改为 GitLab 对应配置和 shell 命令。
  • 配置 push / MR / 手动运行规则，并避免重复创建流水线。
  • 原生产物和报告改用 artifacts；失败日志按需 when: always 保存。
当前接入点GitLab 对应改造
checkout 的 submodules: recursiveGIT_SUBMODULE_STRATEGY: recursive；当前公共 HTTPS 子模块可保留，私有依赖另配访问权限。
$GITHUB_ENV / $GITHUB_PATH改用 CI/CD variables 或同一 job 中的 export；不同 job 重新配置环境。
GITHUB_REPOSITORY + GITHUB_RUN_ID来源记录中的运行链接改用 CI_PIPELINE_URL；提交号仍可由 git rev-parse HEAD 获取。
同一 job 中直接读取生成库拆 job 后通过 artifacts 与 needs:artifacts 传递库；避免依赖共享磁盘残留。
迁移验收仍使用同一组证据：从源码构建、ELF 检查、APK 库哈希一致、220 个 JVM 测试与产物归档。本次只说明迁移方案，未创建或运行 GitLab 流水线。
