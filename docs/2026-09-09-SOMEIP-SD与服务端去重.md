# SOME/IP：服务端去重完成，SD 组播链路待打通

时间：2026-09-09。承接前轮 Android 网络适配与静态 Method 成功，继续开发服务端重复请求处理及 SOME/IP-SD。

## 本轮实现

- 新增独立 C++ `RequestProcessor`，把 16 B payload 校验、去重缓存及内存 snapshot 更新集中处理；Ubuntu 探针服务实际调用该处理器。
- 去重身份为 Client ID + Session ID + 完整 payload；窗口为首次到达起 5 秒、容量 256 条。重复不延长窗口，缓存满时 RC=1，不淘汰仍有效的身份。并发查重与状态更新在同一互斥锁内完成。
- 合法新请求更新 snapshot；重复请求仅复用原 RC；非法帧不改状态。Session 重用但 payload 不同视为新请求。
- Android 新增无静态远端地址的 SD 探针，启用 Wi-Fi MulticastLock，并在启动失败和停止时释放。新增 `CHANGE_WIFI_MULTICAST_STATE` 普通权限。
- 新增 Ubuntu SD 配置、限时抓包脚本、SD PCAP 字段解析与真实去重日志核对脚本。

## SD 阻塞定位

第一次：Android `wlan0` 发出 4 条 FindService，Ubuntu `ens33` 没有业务抓包。
Ubuntu 路由把 `224.244.224.245` 指向 VPN 的 `tun0`，vSomeIP 的 Offer 停留在 pending 队列。

第二次：仅为实验地址临时增加 `224.244.224.245/32 dev ens33`，没有修改默认路由。
Ubuntu 抓到 61 条 OfferService，Service/Instance=`1111/2222`、TTL=3、Endpoint=`192.168.31.248:30509/UDP`。
Android 仍只抓到自身 4 条 FindService；两端都没有收到对方 SD 消息。
因此当前证据定位到两端之间的组播传输链路，尚未确定具体阻塞在模拟器、宿主机、虚拟机网络还是其他转发环节。

Android 日志确认组播锁已获取、`multicastRoute=true`，失败清理时释放了锁。
临时 /32 路由已撤销，服务、抓包进程及 UDP 端口已清理；应用仍以普通应用 UID 运行，未修改 SELinux。
抓包使用已有 adb shell 权限，不代表给应用增加权限。

## 后续边界

1. 在支持双向组播互通的实际链路上复跑同一 SD 探针，确认 Find/Offer 到达、AVAILABLE 与 Method 响应，再验证 StopOffer/TTL 失效。
2. 去重目前是进程内 5 秒窗口，不能保证跨服务重启或无限时间的 exactly-once；假设部署 Client ID 唯一。
3. 尚未实现跨请求 seq 新旧排序、多发送方仲裁和 LVGL 接入；snapshot 目前采用最后到达的合法新请求。
4. 不把静态 Method 成功当作 SD 验收，也不将整个 WP2/LVGL 标为完成。
